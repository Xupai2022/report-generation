# MSS AI PPT 报告生成平台 - 性能需求与指标

## 一、测试环境与方法

### 1.1 测试环境
- **硬件配置**: 标准开发机 (Windows 10/11)
- **Python版本**: 3.x
- **服务器**: FastAPI + Uvicorn (单进程模式)
- **测试工具**: requests + threading (Python标准库)
- **测试日期**: 2026-02-03

### 1.2 测试方法
- **基准测试**: 单线程串行请求，测量20次取统计值
- **压力测试**: 多线程并发请求 (10/20/50并发)
- **资源监控**: 使用 psutil 监控CPU和内存使用

## 二、实际测试结果

### 2.1 API接口响应时间（基准测试）

| 接口 | 平均响应 | P95 | P99 | 最大值 |
|------|---------|-----|-----|--------|
| GET / | 64.28ms | 124.89ms | 124.89ms | 124.89ms |
| GET /api/v1/templates | 54.68ms | 160.95ms | 160.95ms | 160.95ms |
| GET /api/v1/system/health | 60.81ms | 94.64ms | 94.64ms | 94.64ms |
| POST /api/v1/reports (创建作业) | 108.96ms | - | - | 161.10ms |

**测试说明**:
- 所有接口响应时间在 50-110ms 之间
- P95/P99 值在 100-160ms 范围内
- 无请求失败或超时

### 2.2 并发性能测试结果

#### 轻负载 (10并发, 50请求)
- **成功率**: 100% (50/50)
- **响应时间**: 平均 42.57ms, P95 79.37ms
- **吞吐量**: 199.82 req/s
- **资源使用**: CPU 99.7%, 内存 30.0MB

#### 中负载 (20并发, 100请求)
- **成功率**: 100% (100/100)
- **响应时间**: 平均 71.00ms, P95 120.73ms
- **吞吐量**: 215.39 req/s
- **资源使用**: CPU 61.9%, 内存 30.6MB

#### 高负载 (50并发, 200请求)
- **成功率**: 100% (200/200)
- **响应时间**: 平均 61.42ms, P95 101.08ms
- **吞吐量**: 223.15 req/s
- **资源使用**: CPU 59.5%-78.1%, 内存 32.3MB

**测试结论**:
- 系统在50并发下表现稳定，无失败请求
- 吞吐量保持在 200-223 req/s
- 内存占用稳定在 30-32MB
- CPU使用率合理，无资源瓶颈

### 2.3 系统约束与限制

#### 已识别的限流机制
1. **IP级别限流**: 同一IP 30秒内只能提交一次报告生成请求
2. **LLM并发限制**: 最多3个并发LLM请求 (配置在代码中)
3. **速率限制响应**: HTTP 429 + 提示剩余等待时间

## 三、性能需求目标

### 3.1 整体系统目标

#### 响应时间目标
- **常规查询接口** (templates, inputs, health):
  - 平均响应: < 100ms
  - P95: < 200ms
  - P99: < 500ms

- **作业创建接口** (POST /api/v1/reports):
  - 平均响应: < 200ms (仅创建作业，不等待完成)
  - P95: < 500ms
  - P99: < 1000ms

- **报告生成全流程** (含LLM调用):
  - Mock模式: < 10秒
  - 真实LLM模式: < 60秒 (取决于模板复杂度)

- **预览图片生成** (PPTX → PDF → PNG):
  - 单页: < 2秒
  - 10页报告: < 20秒

#### 并发能力目标
- **查询接口**: 支持50-100并发，吞吐量 > 150 req/s
- **报告生成**: 支持3-5并发LLM请求（受限于API成本和速率限制）
- **文件下载**: 支持20-30并发下载

#### 可用性目标
- **成功率**: > 99% (排除用户输入错误)
- **错误恢复**: 失败任务自动重试（最多3次，指数退避）

### 3.2 模块级性能目标

#### A. API路由层 (routers/)

**职责**: 请求验证、限流、作业调度

**性能指标**:
- 请求验证: < 5ms
- 限流检查: < 2ms (内存查找)
- 作业创建: < 50ms (不含实际生成)

**关键点**:
- IP限流: 30秒/次 (可配置)
- 请求参数校验使用 Pydantic (高效)
- 异步作业调度，不阻塞响应

---

#### B. 作业管理层 (services/job_manager.py)

**职责**: 作业状态持久化、并发控制、重试逻辑

**性能指标**:
- 状态读写: < 10ms (文件锁 + JSON序列化)
- 状态查询: < 5ms (内存缓存 + 文件回退)
- 锁获取: < 100ms (跨进程文件锁)

**并发控制**:
- LLM并发信号量: 3 (可配置)
- 文件锁超时: 5秒
- 陈旧锁清理: 启动时自动清理 > 5分钟的锁

**重试策略**:
- 最大重试次数: 3
- 退避策略: 指数退避 (2^retry_count 秒)
- 可重试错误: RateLimitError, 网络超时

---

#### C. LLM编排层 (modules/llm_orchestrator.py)

**职责**: AI内容生成、智能分批、超时控制

**性能指标**:
- 数据提取 (非AI占位符): < 100ms
- 单批次LLM调用: < 30秒 (API超时)
- 完整模板生成: < 60秒 (10页模板)

**优化策略**:
- **智能分批**: 自动将大模板拆分为多批次（每批3-5页）
- **超时控制**: 单次API调用超时30秒
- **Fallback机制**: LLM失败时使用默认占位文本

**资源消耗**:
- 内存: 每个请求 < 50MB
- API调用次数: 1-3次/报告 (取决于模板大小)

---

#### D. PPT生成层 (modules/ppt_generator.py)

**职责**: PPTX文件渲染、图表绘制、Token替换

**性能指标**:
- Token替换: < 100ms (纯文本处理)
- 单个图表绘制: < 200ms (原生PowerPoint图表)
- 完整报告渲染: < 2秒 (10页模板)

**文件操作**:
- 模板加载: < 100ms (缓存)
- 文件写入: < 500ms (使用文件锁)
- 临时文件清理: 异步执行

**内存管理**:
- 单报告内存占用: < 30MB
- 模板缓存: 常用模板常驻内存

---

#### E. 预览生成层 (modules/preview_generator.py)

**职责**: PPTX → PDF → PNG 转换链

**性能指标**:
- PPTX → PDF (LibreOffice): 单页 1-1.5秒
- PDF → PNG (PyMuPDF): 单页 < 0.5秒
- 10页报告完整转换: < 20秒

**依赖约束**:
- **必须安装**: LibreOffice (外部依赖)
- **超时控制**: LibreOffice转换超时60秒
- **并发限制**: 单进程串行执行（LibreOffice限制）

**资源消耗**:
- 内存峰值: 单个转换任务 < 200MB
- 磁盘IO: 临时文件写入，转换后自动清理

**优化建议**:
- 预览图片定期清理（默认7天）
- 可配置图片质量以平衡速度和清晰度

---

#### F. 数据验证层（已移除）

**职责**: 关键数值校验、数据一致性检查

**性能指标**:
- 单字段验证: < 1ms
- 完整报告验证: < 50ms (验证10-20个关键字段)

**验证范围**:
- 数值字段: 精确匹配
- 枚举字段: 范围检查
- 必填字段: 存在性检查

---

#### G. 文件锁管理 (modules/file_lock.py)

**职责**: 跨进程文件访问同步

**性能指标**:
- 锁获取: < 100ms (无竞争)
- 锁释放: < 5ms
- 陈旧锁检测: < 50ms (遍历目录)

**可靠性**:
- 自动清理: 启动时清理 > 5分钟的锁
- 异常恢复: 进程崩溃后锁自动失效
- 跨平台: Windows (msvcrt) + Linux (fcntl)

---

#### H. 会话管理 (modules/session_manager.py)

**职责**: 会话隔离、并发请求目录管理

**性能指标**:
- 会话创建: < 10ms
- 目录清理: 后台异步执行

**存储策略**:
- 每个作业独立目录: `{input_id}_{timestamp}_{template_id}`
- 并发请求完全隔离
- 可选清理策略（默认保留7天）

### 3.3 基础设施与部署要求

#### 推荐配置

**开发/测试环境**:
- CPU: 2核 (单进程运行)
- 内存: 1GB (包含操作系统)
- 磁盘: 10GB (代码 + 输出文件)
- 网络: 普通宽带 (主要受限于LLM API延迟)

**生产环境**:
- CPU: 4核 (支持多进程部署)
- 内存: 2-4GB
- 磁盘: 50GB (SSD推荐，用于预览图片缓存)
- 网络: 稳定互联网连接 (LLM API调用)

#### 扩展性建议

**水平扩展**:
- 使用 Nginx/Gunicorn 部署多进程
- 每个进程3个LLM并发 → N进程 = 3N并发
- 建议: 4进程 = 12并发LLM请求

**存储扩展**:
- 输出目录定期清理（7-30天）
- 可选: 使用对象存储 (S3/OSS) 存储生成的报告
- 预览图片压缩或降低分辨率

**数据库 (当前未使用)**:
- 当前: 文件系统存储 (JSON)
- 可选升级: SQLite → PostgreSQL (支持更高并发)

## 四、性能优化建议

### 4.1 已实现的优化

✅ **智能分批**: LLM调用自动拆分大模板
✅ **异步作业**: 报告生成后台执行，立即返回响应
✅ **文件锁**: 防止并发写入冲突
✅ **限流保护**: IP级别限流防止滥用
✅ **模板缓存**: 常用模板加载后缓存
✅ **重试机制**: 失败任务自动重试（指数退避）
✅ **资源清理**: 陈旧锁和旧文件自动清理

### 4.2 可选优化方向

#### 短期优化 (1-2周)
1. **数据库引入**:
   - 用SQLite替代JSON文件存储作业状态
   - 减少文件锁竞争
   - 支持更复杂的查询（作业历史、统计）

2. **预览缓存**:
   - 相同输入+模板的预览图片复用
   - 使用哈希值作为缓存键
   - 节省70%+ LibreOffice转换时间

3. **响应流式传输**:
   - WebSocket实时推送生成进度
   - 用户体验提升

#### 中期优化 (1-2月)
1. **LLM响应缓存**:
   - 缓存常见数据模式的LLM输出
   - 使用向量相似度匹配
   - Mock模式自动化

2. **多进程部署**:
   - Gunicorn + N进程
   - 共享数据库状态
   - 提升3-5倍并发能力

3. **图片异步生成**:
   - 报告生成后立即返回
   - 预览按需异步生成
   - 减少用户等待时间

#### 长期优化 (3-6月)
1. **分布式队列**:
   - Celery/RQ 替代内存队列
   - 支持跨机器任务分发
   - 提升可靠性和扩展性

2. **CDN集成**:
   - 静态资源和预览图片通过CDN分发
   - 减轻服务器压力

3. **AI模型本地化**:
   - 部署本地LLM模型（如GLM）
   - 减少API调用成本
   - 更快的响应时间（无网络延迟）

## 六、总结

### 当前系统评估

**优势**:
- 基础响应性能良好（50-110ms）
- 并发处理稳定（50并发无失败）
- 内存占用合理（< 35MB）
- 代码架构清晰，易于优化

**瓶颈识别**:
1. **LLM调用延迟**: 主要耗时环节（10-60秒）
2. **预览生成**: LibreOffice转换较慢（1.5秒/页）
3. **串行限制**: 预览生成无法并发
4. **限流过严**: 30秒/次可能影响正常用户

**性能目标达成度**:
- ✅ 查询接口: 平均响应 < 100ms
- ✅ 并发能力: 支持50并发
- ⚠️ 报告生成: 需实际LLM测试验证
- ⚠️ 预览生成: 需LibreOffice环境测试

### 部署建议

**最小化部署** (1-10用户):
- 单进程 FastAPI
- 文件系统存储
- 当前配置即可

**标准部署** (10-100用户):
- 4进程 Gunicorn
- SQLite数据库
- 定期清理旧文件

**企业部署** (100+用户):
- 8+进程 Gunicorn
- PostgreSQL + Redis
- 对象存储 (S3/OSS)
- 负载均衡

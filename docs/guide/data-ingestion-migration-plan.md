# 数据接入迁移方案

本文面向当前仓库的报告生成链路，给出一套保留现有 Excel 处理流程、并行引入接口/数据库取数框架的详细计划。目标是在不扰动后续报告生成流程的前提下，把新的数据来源统一映射为与当前 `input.json` 等价的结构。

## 1. 背景与目标

当前系统已经存在一条稳定链路：

`Excel -> ExcelDataExtractor -> session input.json -> TenantInput -> 报告生成`

其中，后续报告生成主要消费的是 `TenantInput.raw`，而不是 Excel 本身。因此下一阶段不建议直接改造报告生成逻辑，而应新增一套独立的数据接入与处理框架，将接口或数据库中的数据加工后写入与当前一致的 `input.json` 结构。

本次迁移的目标如下：

- 保留现有 Excel 上传和 Excel 解析流程，作为当前稳定路径和回退方案。
- 新增一套面向接口、MongoDB 等数据源的标准化处理框架。
- 新框架的最终产物仍然是当前格式的 `input.json`。
- 报告生成、AI 改写、预览、导出等后续流程对新旧数据来源无感。
- 在迁移早期支持 Excel 与新数据源双轨运行、结果比对和灰度切换。

不在本阶段处理的内容：

- 不重写 `LLMOrchestrator`、`PPTGenerator`、`SlideSpec` 等后续模块。
- 不强行移除 Excel 入口。
- 不在第一阶段追求所有模板同时切换。

## 2. 当前事实边界

从当前代码可以确认以下事实：

- `ReportService` 最终消费的是 `TenantInput(raw=...)`。
- session 目录下存在运行时 `input.json`，后续流程可直接复用它。
- 当前 Excel 运行时解析逻辑位于 `ExcelDataExtractor`。
- 当前手工改写回写 `input.json` 的逻辑已经依赖 placeholder source path。

这说明新的数据接入方案最适合插入在“构造 `TenantInput`”这一层，而不是插入到 PPT 生成或 AI 编排层。

## 3. 总体设计原则

### 3.1 保持后半段稳定

新方案只替换“输入构造阶段”，不替换“报告生成阶段”。  
也就是：

- 允许 `Excel -> input.json`
- 也允许 `API/MongoDB -> input.json`
- 但 `input.json -> TenantInput -> generate()` 维持一致

### 3.2 建立标准中间模型

不要让模板或报告逻辑直接依赖平台接口字段名、MongoDB 表结构、集合名称或查询语句。  
应该先把上游多源数据整理为内部统一的标准数据模型，再映射到 `input.json`。

### 3.3 业务加工与数据采集分离

“取数”与“整理指标”要明确分层：

- 采集层负责拿到原始数据
- 加工层负责模拟用户整理 Excel 的过程
- 映射层负责把加工结果写入目标 `input.json` 路径

### 3.4 双轨验证优先

迁移初期不直接替换 Excel，而是让新方案先输出同结构结果，与现有 Excel 结果做比对。  
先验证“数据等价性”，再考虑切换实际入口。

### 3.5 按“原始收集表格”拆分处理单元

已知当前用户工作流不是直接维护一个原始总表，而是先从多个平台或部门导出多个表格，再人工汇总到一个最终 sheet。  
因此新框架应尽量贴近这一现实工作流：

- 不建议一开始做一个大一统的全局处理器
- 建议按“原始收集表格”或“业务域表”拆分处理单元
- 每个处理单元独立取数、独立加工、独立产出子结果
- 最后再统一汇总成当前 `input.json`

这种组织方式的好处是：

- 更贴近人工整理流程，便于业务对照
- 更容易定位某一张表对应的数据问题
- 某个来源缺失时，影响范围更容易控制
- 后续替换某一类来源时，改动边界更清晰
- 更适合做分表级的新旧结果比对

### 3.6 最终送入 `input.json` 前必须参考当前 Excel 处理逻辑

这是本次迁移的最高优先级原则。

无论上游数据来自：

- 平台接口
- MongoDB
- 其他数据库
- 多表汇总后的中间结果

在最终写入 `input.json` 之前，都必须参考当前 Excel 提取流程中的后处理逻辑，对数据进行最终整理，以保证 PPT 的显示效果与当前链路保持一致。

这里强调的不是“沿用 Excel 载体本身”，而是“沿用当前 Excel 处理逻辑里已经被验证过、直接影响 PPT 展示效果的后处理规则”。

必须优先保留和迁移的通常包括：

- 数值格式化方式
- 百分比、万、整数、小数位处理
- 图表序列结构与顺序
- 标签文本拼装方式
- 缺失值兜底策略
- TopN 截取与排序规则
- 趋势数据组织方式
- 最终字段类型要求

不应丢失或随意改变的原因是：

- `input.json` 不只是数据容器，它还隐含承载了 PPT 模板对字段形态的预期
- 只做字段映射而不做最终后处理，往往会导致 PPT 文案显示异常、图表格式异常、数值风格不一致
- 从业务角度看，PPT 的显示效果和现有产出一致，是本次迁移成功的首要标准

因此迁移时必须把当前 Excel 逻辑拆成三类：

1. Excel 载体解析逻辑  
例如 sheet 名、单元格坐标、区域读取方式。  
这部分不需要迁移。

2. 通用归一逻辑  
例如基础类型转换、空值归一、文本清洗。  
这部分可按需迁移。

3. 影响最终 `input.json` 展示效果的后处理逻辑  
例如数值格式、图表结构、排序、标签输出。  
这部分必须迁移，并且在最终写入 `input.json` 前执行。

换句话说，新框架可以替换 Excel 的“取数方式”，但不能绕过当前 Excel 处理流程中对最终 PPT 效果负责的那一层后处理。

## 4. 目标架构

建议新增如下逻辑分层：

### 4.1 Source Collector

负责从不同来源获取原始数据：

- HTTP API
- MongoDB
- 后续可扩展 SQL、文件、对象存储等

职责边界：

- 认证
- 请求重试
- 分页
- 限流
- 游标/增量取数
- 原始响应落日志或调试快照

不负责：

- 报表口径计算
- 模板字段映射

### 4.2 Domain Transformer

负责把原始数据转成内部业务结构，并沉淀“人工整理 Excel”的规则：

- 时间窗过滤
- 字段归一
- 指标聚合
- 去重
- 分类映射
- TopN 排序
- 趋势统计
- 百分比/占比换算
- 缺失值兜底
- 多来源拼接

这一层是整个迁移的核心。  
真正有价值的不是“把 Excel 改成接口”，而是把原本隐藏在人工作业里的业务口径显式化。

### 4.3 Input Mapper

负责把领域加工结果映射到当前报表依赖的 `input.json`。

职责边界：

- 将标准字段写入固定路径
- 按当前模板需要的键名和嵌套结构组织数据
- 生成与当前 `ExcelDataExtractor` 产物一致的结构和格式
- 在最终落盘前执行与现有 Excel 处理逻辑对齐的展示型后处理

不负责：

- 上游采集
- 复杂统计

### 4.4 Input Runtime Builder

作为对 `ReportService` 的适配入口，按数据来源选择：

- 走现有 Excel runtime parser
- 或走新的 API/DB runtime builder

其输出统一为：

- session 下的 `input.json`
- 内存中的 `TenantInput`

### 4.5 Final Assembler

在多表模式下，建议再显式增加一个最终汇总层。

职责边界：

- 接收多个“表格处理单元”的输出
- 合并为完整报表输入结构
- 处理跨表依赖、冲突字段、缺省值
- 统一写入最终 `input.json`

推荐链路如下：

`表格单元A -> 子结果A`
`表格单元B -> 子结果B`
`表格单元C -> 子结果C`
`...`
`Final Assembler -> input.json -> TenantInput`

## 5. 推荐模块拆分

建议在后端新增独立的数据接入模块，例如：

```text
backend/
  services/
    data_ingestion/
      models/
      collectors/
      transformers/
      mappers/
      validators/
      assemblers/
      runtime_builder.py
```

建议职责如下：

### 5.1 `models/`

定义内部标准模型与配置模型，例如：

- 原始取数参数
- 时间范围
- 租户标识
- 平台类型
- 标准领域对象
- 构建结果摘要

优先使用 `pydantic` 建模，便于：

- 字段校验
- 类型归一
- 调试
- 序列化

### 5.2 `collectors/`

按来源拆分：

- `api_collector.py`
- `mongo_collector.py`
- `composite_collector.py`

建议每个 collector 只返回“原始或轻度清洗后的数据”，不要直接返回模板字段。

### 5.3 `transformers/`

按业务主题拆分，而不是按技术来源拆分，例如：

- `coverage_transformer.py`
- `incident_transformer.py`
- `asset_transformer.py`
- `vulnerability_transformer.py`
- `threat_transformer.py`

这样未来即使某个主题的数据来源变化，业务口径仍集中在同一处维护。

### 5.4 `mappers/`

负责从标准业务模型到 `input.json` 的映射，例如：

- `classic_ops_mapper.py`
- `classic_ops_v2_mapper.py`

如果不同模板共享大部分字段，可先抽公共 mapper，再做模板特化。

### 5.5 `validators/`

用于校验：

- 必填字段是否齐全
- 数值范围是否合法
- 图表数据长度是否匹配
- 百分比和数值格式是否满足模板预期

### 5.6 `assemblers/`

用于多表汇总场景下的最终组装，例如：

- `classic_ops_assembler.py`

职责包括：

- 合并多个表格处理结果
- 统一管理冲突字段优先级
- 为最终 mapper 提供完整上下文

### 5.7 `runtime_builder.py`

对 `ReportService` 提供统一调用接口，例如：

- `build_from_excel(...)`
- `build_from_sources(...)`
- `build_for_session(...)`

该层负责：

- 调用 collector
- 调用 transformer
- 调用 assembler
- 调用 mapper
- 写 session `input.json`
- 返回 `TenantInput`

## 6. 技术选型建议

### 6.1 主框架

建议采用以下组合：

- HTTP 接口：`httpx`
- MongoDB：`pymongo`
- 数据模型：`pydantic`
- 业务编排：普通 Python service

### 6.2 关于 `pandas`

本项目里不建议一开始就让 `pandas` 成为数据处理主框架。

更适合的策略是：

- 主体规则用普通 Python + `pydantic`
- 仅在局部需要明显表格化统计时按需使用 `pandas`

适合局部使用 `pandas` 的场景：

- 大量明细聚合
- 按月统计
- 多维 group by
- 透视表型转换

不适合用 `pandas` 作为主干的原因：

- 最终目标是嵌套 JSON，不是分析型表格
- 很多逻辑是业务规则，不是纯数据分析
- 可读性、可调试性和异常定位在 service 风格里更好控制

### 6.3 MongoDB 策略

对于 MongoDB，建议优先把粗筛选和基础聚合尽量下沉到 aggregation pipeline，避免无意义地把大量明细拉回 Python。

建议原则：

- 过滤、分组、计数、排序优先在 MongoDB 做
- 复杂业务口径、跨来源拼接、模板格式化在 Python 做

## 7. 数据契约设计

### 7.1 三层数据契约

建议显式定义三层契约：

1. 原始契约  
来自接口或数据库的原始结构。

2. 标准业务契约  
系统内部统一的领域结构，例如：
- 覆盖率摘要
- 告警趋势
- 漏洞闭环
- 资产分布

3. 报表输入契约  
当前 `input.json` 的最终结构。

### 7.2 `input.json` 作为稳定边界

当前阶段应把 `input.json` 看成迁移稳定边界：

- 前半段可以重构
- 后半段尽量不动

后续如果模板体系再演进，可以考虑从 `input.json` 进一步升级为更通用的 canonical input schema，但不建议在本阶段同时做两次抽象。

### 7.3 推荐采用“多表子结果 -> 最终汇总”契约

针对当前业务，更推荐采用如下契约：

1. 原始来源契约  
每个接口或数据库查询返回自己的原始结构。

2. 表格级子结果契约  
每张“原始收集表格”对应一个清晰的中间结果对象。

3. 汇总后报表输入契约  
由 assembler 将多个子结果合并成最终 `input.json`。

这样做的关键收益是：  
上游可以按表格逐块建设，下游仍然只面对一个稳定的最终输入结构。

## 8. 迁移实施计划

### 阶段 0：口径梳理

目标：

- 识别当前 Excel 每个字段的业务含义
- 区分“原始数据字段”和“加工后指标字段”
- 整理人工 Excel 处理步骤

输出物：

- 字段口径表
- 数据来源清单
- 指标计算说明
- Excel 字段到 `input.json` 路径映射表

完成标准：

- 能明确说明 `input.json` 中每个关键字段来自哪里、怎么算、缺失时怎么处理

### 阶段 1：标准模型与框架落地

目标：

- 建立数据接入模块骨架
- 定义 collector / transformer / mapper 接口
- 定义多表子结果与 assembler 接口
- 支持把处理结果写入 session `input.json`

输出物：

- 数据接入目录结构
- 标准模型定义
- assembler 定义
- runtime builder
- 基础日志与错误模型

完成标准：

- 可以跑通一个最小链路，将 mock API 或 mock DB 数据写成合法 `input.json`

### 阶段 2：单主题打通

目标：

- 先挑一张最明确的原始收集表完成端到端迁移，例如告警表或漏洞表
- 形成可复制模式

输出物：

- 某一张表对应的 collector
- 对应 transformer
- 对应子结果模型
- 对应 assembler 接入
- 对应 mapper
- 与 Excel 结果的对比脚本

完成标准：

- 该主题的新旧结果误差可解释、可复现

### 阶段 3：全量主题接入

目标：

- 按原始收集表格逐步替换人工 Excel 整理过程
- 形成完整 `input.json`

输出物：

- 所有主题的接入与转换逻辑
- 多表汇总逻辑
- 缺失字段策略
- 多来源拼接规则

完成标准：

- 新流程可以独立产出完整 `input.json`

### 阶段 4：双轨比对与灰度

目标：

- Excel 与新流程并行运行
- 自动对比输出差异
- 收敛口径偏差

输出物：

- diff 报告
- 误差阈值规则
- 灰度开关

完成标准：

- 核心模板关键字段差异在可接受阈值内

### 阶段 5：正式切换

目标：

- 对指定模板或租户切换到新数据接入路径
- Excel 保留为回退入口

输出物：

- 切换开关
- 回滚方案
- 运行监控面板或日志指标

完成标准：

- 新链路稳定运行一段时间，且可快速回退

## 9. 映射策略建议

### 9.1 不直接写分散路径

不要在 collector 或 transformer 内部直接散落地写 `input.json` 路径。  
应把路径写入集中 mapper 中维护。

在多表模式下进一步建议：

- collector 不写 `input.json`
- transformer 不写 `input.json`
- assembler 不直接处理底层取数
- mapper 统一负责最终路径落点

### 9.2 先对齐结构，再对齐格式

建议分两步验证输出：

1. 结构是否一致
- 键名
- 嵌套层级
- 数组对象结构

2. 格式是否一致
- 数值类型
- 百分比文本
- 小数位
- 图表数组长度

在当前项目里，这里的“格式一致”不是次要要求，而是核心验收项。  
必须明确把“最终 PPT 显示效果一致”置于最高优先级，必要时优先保持显示效果，再回头优化中间实现。

### 9.3 保持 source path 可追踪

当前系统已有 placeholder source path 机制。  
新方案中应继续维护“某个 `input.json` 字段来源于哪个业务指标”的追踪能力，便于：

- 调试
- 手工改写回写
- 差异分析

## 10. 测试与验证计划

### 10.1 单元测试

覆盖重点：

- collector 的分页、重试、异常处理
- transformer 的口径计算
- mapper 的路径映射
- validator 的格式校验

### 10.2 对比测试

准备一批真实或脱敏样本：

- 同一时间窗下
- 同一租户下
- 由 Excel 路径和新路径分别生成 `input.json`

然后做：

- 结构 diff
- 数值 diff
- 图表序列 diff

### 10.3 集成测试

验证新 `input.json` 喂给现有报告生成链路后：

- 能正常生成 slidespec
- 能正常生成 PPT
- 能正常生成 preview
- 不影响 AI 改写和导出

## 11. 风险与应对

### 11.1 最大风险：业务口径不清

真正难点不在技术，而在“用户当初怎么整理 Excel”。  
应对方式：

- 做字段口径表
- 让业务方确认
- 用样本比对驱动修正

### 11.2 多来源字段冲突

不同平台或数据库可能对同一指标定义不同。  
应对方式：

- 建立优先级策略
- 显式记录字段来源
- 缺失与冲突时输出 warning

### 11.3 结果与 Excel 不一致

这是迁移中最常见的问题。  
应对方式：

- 双轨运行
- 差异报告
- 为每个关键指标定义解释和容差

### 11.4 过早把逻辑写死在数据源适配器里

如果在 collector 里混入太多业务规则，后续将很难扩展。  
应对方式：

- 强制分层
- code review 时重点检查职责边界

## 13. 近期执行建议

建议按以下顺序推进：

1. 先按“用户原始收集表格”列出清单，并梳理每张表到最终汇总 sheet 的关系
2. 整理当前 Excel 到 `input.json` 的映射表
3. 选一张结构最清晰的表做试点
4. 完成新的 collector + transformer + assembler + mapper 最小闭环
5. 让新旧链路并行跑并产出 diff
6. 收敛口径后再逐表扩大范围

## 14. 结论

本项目下一阶段最合适的演进方式，不是直接用接口或数据库替换 Excel 文件本身，而是新增一套独立的数据接入与处理框架，并继续把最终结果映射成当前的 `input.json`。这样可以把风险控制在输入构造阶段，保持后续报告生成链路稳定，同时为未来接入更多平台和数据源留出清晰扩展位。

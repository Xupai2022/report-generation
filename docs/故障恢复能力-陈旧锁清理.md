# 故障恢复能力 - 陈旧锁文件自动清理

## 问题描述

在并发文件操作场景中，如果进程在持有文件锁时崩溃（例如：程序异常退出、系统断电、强制终止等），文件锁（`*.lock`）会残留在磁盘上。这些陈旧的锁文件会导致：

1. **新请求被阻塞**：尝试获取相同文件锁的请求会一直等待，直到超时失败
2. **需要手动干预**：运维人员需要手动删除残留的锁文件
3. **服务不可用**：如果关键文件被锁定，整个服务可能无法正常工作

### 2. 陈旧锁清理函数（已存在）

**函数**: `cleanup_stale_locks(directory, max_age_seconds=300)`

**功能**:
- 递归扫描指定目录中的所有 `*.lock` 文件
- 根据文件修改时间判断是否陈旧（默认：5分钟）
- 自动删除超过指定年龄的锁文件

**实现**:
```python
def cleanup_stale_locks(directory: Path, max_age_seconds: int = 300):
    """Clean up stale lock files older than specified age.

    This is useful for cleaning up locks from crashed processes.

    Args:
        directory: Directory to scan for lock files
        max_age_seconds: Maximum age before considering lock stale (default: 300 = 5 minutes)
    """
    current_time = time.time()
    cleaned_count = 0

    for lock_file in directory.rglob("*.lock"):
        try:
            stat = lock_file.stat()
            age = current_time - stat.st_mtime

            if age > max_age_seconds:
                lock_file.unlink()
                cleaned_count += 1
                logger.info(f"Cleaned up stale lock: {lock_file}")
        except Exception as e:
            logger.warning(f"Error cleaning lock {lock_file}: {e}")

    if cleaned_count > 0:
        logger.info(f"Cleaned up {cleaned_count} stale locks in {directory}")
```

### 3. 启动时自动清理（新增）

**文件**: [mss_ai_ppt_sample_assets/backend/app.py](mss_ai_ppt_sample_assets/backend/app.py:736-753)

**修改内容**:

```python
@app.on_event("startup")
async def startup_cleanup():
    """Clean up old sessions and stale locks when server starts."""
    try:
        # Clean up old sessions (older than 24 hours)
        cleaned_count = service.cleanup_old_sessions(max_age_hours=24)
        if cleaned_count > 0:
            logger.info(f"🧹 Startup cleanup: removed {cleaned_count} old sessions")

        # Clean up stale lock files (older than 5 minutes)
        # These locks may be left behind by crashed processes
        from mss_ai_ppt_sample_assets.backend.modules.file_lock import cleanup_stale_locks
        outputs_dir = Path(__file__).parent / "outputs"
        cleanup_stale_locks(outputs_dir, max_age_seconds=300)  # 5 minutes
        logger.info("🔓 Startup cleanup: stale locks cleaned")

    except Exception as e:
        logger.warning(f"⚠️ Startup cleanup failed: {e}")
```

**工作流程**:

1. **服务器启动** → 触发 `startup_cleanup()` 事件
2. **清理旧会话** → 删除24小时以上的会话目录
3. **清理陈旧锁** → 删除5分钟以上的 `*.lock` 文件
4. **记录日志** → 输出清理结果到日志

## 配置说明

### 陈旧锁判断标准

**默认值**: 300秒（5分钟）

**原因**:
- 正常文件操作通常在几秒内完成
- 5分钟足够长，避免误删正在使用的锁
- 5分钟足够短，避免长时间阻塞

**调整方法**:
```python
# 在 app.py 中修改 max_age_seconds 参数
cleanup_stale_locks(outputs_dir, max_age_seconds=600)  # 改为10分钟
```

### 清理目录范围

**默认**: `mss_ai_ppt_sample_assets/backend/outputs/`

**覆盖范围**:
- `outputs/sessions/` - 会话目录中的锁
- `outputs/reports/` - 报告文件锁
- `outputs/slidespecs/` - 规格文件锁
- `outputs/previews/` - 预览文件锁
- 所有子目录递归扫描

## 故障场景示例

### 场景 1: 进程崩溃

**问题**:
```
1. 用户A请求生成报告
2. 系统创建 report.pptx.lock
3. 进程崩溃（异常退出）
4. 锁文件残留
5. 用户B请求相同报告 → 超时失败
```

**解决**:
```
1. 服务器重启
2. startup_cleanup() 自动运行
3. 检测到 report.pptx.lock 超过5分钟
4. 自动删除陈旧锁
5. 用户B可以正常请求
```

### 场景 2: 系统断电

**问题**:
```
1. 多个并发请求正在执行
2. 每个请求持有各自的文件锁
3. 服务器断电
4. 重启后所有锁文件残留
```

**解决**:
```
1. 服务器恢复后启动
2. startup_cleanup() 扫描 outputs/
3. 发现多个超过5分钟的 *.lock 文件
4. 全部自动删除
5. 系统恢复正常服务
```

### 场景 3: 手动终止进程

**问题**:
```
1. 运维人员发现进程占用过高
2. 使用 kill -9 强制终止进程
3. 锁文件未正常释放
```

**解决**:
```
1. 重新启动服务
2. 自动清理残留锁
3. 无需手动干预
```

## 最佳实践

- ✅ 使用默认的5分钟超时（适合大多数场景）
